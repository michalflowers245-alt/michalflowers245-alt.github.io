01

项目与问题

从活动想法到可承接的需求

Mazi 面向北美本地现场活动，连接想参加活动的人、愿意承接的主办方与平台运营者。很多活动在筹备时并不知道有多少人愿意来、愿意付多少钱，而参与者也难以判断一场活动究竟只是想法，还是已经确定举办。

产品先收集城市、活动偏好和愿付价格，再由主办方承接，进入报名、票券与履约。Mazi 是当前产品名，Rally 和 LocalLive 是历史材料中的名称。

02

本人角色

我的角色与协作边界

我参与需求研究、产品方案与技术协作，把线下活动中的意向收集、价格确认、主办方承诺和现场交付，拆成参与者、主办方与平台各自的操作流程。工作重点是明确每个角色在什么状态下可以做什么，以及出现问题后由谁承接。

我把人数与价格、锁单、付款协议、失败补缴和履约材料转成可检查的规则，衔接页面、工程与交付说明；前后端开发、支付服务与测试由团队协作完成。

03

目标与关键判断

意向、报名与成行的边界

点场板收集“想看什么、在哪里、愿付多少”的需求；点赞、收藏和价格信号帮助主办方判断兴趣，但不是付费报名。主办方认领后，点场与正式活动关联，用户再进入清楚的参与流程。

正式活动的当前人数影响票价：工程中的众筹定价在起步人数与容量上限之间线性降价，并设置价格边界。用户的最高可接受价格低于当前报价时，进入等待路径，而不是直接当成有效付款订单。

成团与锁单也分开：满足人数条件后，仍需主办方确认举办。用户支付协议解释定金、尾款、取消与退款；活动方结算协议解释举办责任、履约材料与结算。协议内容、确认记录和服务端状态一起帮助回查用户当时接受的规则与后续处理过程。

材料说明公开网站的机制页介绍人数越多、票价线性降低；点场承接、等待订单以及协议展示与确认记录，另由仓库实现与历史验证材料说明。

04

推进流程

三方流程：从点场到履约

  1. 表达需求：参与者提交活动偏好、地点与愿付价格；其他用户留下支持或价格信号，主办方从点场需求中寻找可以承接的活动。
  2. 组织承接：主办方认领需求并关联正式活动，设置活动内容、人数、容量与价格条件。平台承担相应审核与运营管理。
  3. 收费报名：参与者查看当前价格、可接受上限与参与条件，确认协议并进入定金流程；达到人数条件并由主办方确认举办后，进入适用的冷静期。
  4. 锁单出票：到锁单节点、主办方确认锁单后，系统计算尾款及适用服务费，在线完成应付金额确认；付款成功的订单才能取得有效票券，而不是到现场才扣尾款。
  5. 现场与履约：主办方核销票券，活动结束后提交履约证据；平台审核通过后推进剩余票款结算。订单状态、票券状态和结算记录分别留痕。

免费活动是另一条路径：用户确认报名后进入已报名与出票状态，不经过定金、尾款或资金账本。这让同一套活动组织与核销能力可以服务不同活动类型，而不是让免费报名伪装成一笔零元众筹支付。

05

核心产品或机制

产品模块与角色分工

点场板以活动标题、地区、待接办状态和支持数组织需求；城市探索承接地区入口。产品围绕参与者、主办方和平台运营者划分操作权限与业务状态。

  • 公开入口：品牌首页、城市探索、活动列表、众筹机制说明与观众／主办方双入口。中文与英文切换、桌面与手机布局均有实际页面。
  • 参与者端：点场需求、支持与收藏、众筹报名、价格等待、定金与尾款、票夹和通知。需求表达与正式参与分别管理。
  • 主办方端：认领点场、创建和编辑活动、确认成行与锁单、查看订单、现场核销、提交履约材料和查询结算。
  • 平台端：审核主办方、点场与履约证据，管理活动，处理订单、退款、审计、通知与对账；与用户和主办方界面分开授权。

06

代表案例与材料

异常处理与出票门槛

尾款失败，不直接出票

  1. 记录失败锁单扣款失败后记录原因，订单进入补缴状态，而不是显示成功。
  2. 保留补缴用户在 24 小时期限内重试；主办方区分已付款与待补缴订单。
  3. 确认出票服务端确认补缴成功才生成票券；超时按规则结束补缴、不出票。

我参与规则与技术协作，将失败记录、补缴期限与出票条件转成可检查的流程。

补缴订单保留失败原因、处理期限与下一步操作；页面提示须与服务端确认对应，便于参与者处理，也方便主办方区分订单状态。

定金失败保持未付款；支付回调需要防止重复处理，重复结算不能重复记账。活动状态与支付状态分开记录，便于发现“活动已锁单但某笔订单仍待补缴”等情况。

到现场后，核销还要核对票券所属活动、主办方权限与使用状态，防止跨活动核销和重复扫码。活动结束也不意味着自动完成所有结算，剩余票款继续受履约材料与运营审核约束。

交付将前端操作与业务服务对应：参与者接口记录需求与支持，主办方接口处理认领并关联正式活动；免费活动使用独立报名与出票分支。

历史验证分开记录：2026年8月28日隔离实例为后端127项、前端31项通过；8月29日旧 Docker 实例为107项与29项通过，不能合并或替代新版验收。2026年10月10日已记录公开首页、机制说明、活动入口与纽约城市页；线上部署与仓库主分支仍需逐项对版。

  • 界面层：Next.js App Router 承接发现、点场、活动及各角色页面，配合 Tailwind 与 Zustand 管理表现和交互状态。
  • 业务层：FastAPI 与 Pydantic 按参与者、主办方和管理员划分接口；定价、报名、支付、票券、结算与通知分别由对应服务承接。关键状态推进在服务端确认。
  • 数据层：Supabase 承接 Postgres、身份认证与文件存储。数据库迁移、订单和支付记录、金额快照、账本及审计资料共同支撑回查，而不只保存一条“支付成功”。
  • 交付层：产品说明、业务规则、三方前后端工程、数据库迁移、测试文件、部署清单、定时任务与运维脚本。支付回调、补缴超时、邮件重试与主动对账均有对应处理。
